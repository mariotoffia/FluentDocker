# Production Readiness Issues

Generated: 2026-07-03

Scope: adversarial multi-agent audit of FluentDocker production readiness (10 subagents, one per subsystem/driver). Each agent was instructed to assume the prior 54-issue fix commit (`d2d2b7e`) may be cosmetic, incomplete, or regressive, and to verify skeptically with file:line evidence. No fixes were applied.

## Executive summary

Overall verdict: **not production ready**. Zero bugs: **no** — 171 findings across 10 subsystem reviews: **15 Critical, 61 Major, 95 Minor**. Several Criticals were empirically confirmed, not inferred: the SSE crash (DMR-1) was reproduced with a standalone .NET repro, the CLI argv corruption (CLI-1) with a live argument-parsing harness, the net8.0 TLS break (API-1) is red in the repo's own CI at HEAD, and the 0777 build-context tar (API-3) was proven against SharpCompress 0.48.0.

Answers to the six audit questions:

1. **Is the code production ready?** No. Every subsystem except docs structure carries at least one Critical or a cluster of Majors. The core engines (CLI process execution, API transport/disposal, kernel happy path, builder cleanup machinery, model-runner mock infrastructure) are genuinely well built — the failures are concentrated at the edges the happy path never visits.
2. **Is the documentation production ready?** No, but close. ~97% of 349 compile-verified snippets compile as written and Examples build clean — yet architecture.md documents a fictional capabilities API (DOC-1), the CHANGELOG recommends a pattern that does not compile (DOC-2), the NuGet package README will contradict itself the day 3.2.0 ships (DOC-5), and there is no troubleshooting page anywhere.
3. **Do we have zero bugs?** No. Highlights: streaming inference crashes on emoji (DMR-1); TLS+CA throws at construction on net8.0 (API-1); `follow=true` API logs hang and OOM (API-2); `KeepRunning()` force-removes the running container (BLD-1); disposing an attached compose project destroys user-owned resources (SVC-1); Podman stats/network/event parsers cannot parse real podman ≥4 output (POD-2/3/4); Docker CLI event stream returns anonymous events (COM-1); `ComposeServiceBuilder.Volume` crashes on any options (BLD-2).
4. **Is the code resilient — outages and recovery?** Partially. Real, tested hardening exists: dispose budgets, process-tree kills, cancellation propagation, typed connection errors, machine auto-start locks. But: unbounded hangs remain (DMR-2 header-wait, API-2 follow logs, TST-4 dispose deadlock, EngineScope restore with no budget); error taxonomy is systematically erased at the service/driver boundary (CLI-5, SVC-8, POD-11) so daemon-down is indistinguishable from not-found; `IsTransient` is never set — the advertised retry discriminator is dead; and the shared primitives prefer silent defaults (NullLogger sinks, TryDeserialize→default, silent zeros, silent delete failure) that mask outages instead of surfacing them.
5. **Is the library easy to consume and understand?** Mostly yes — the fluent surface, typed `BuildResults`, `CommandResponse<T>` consistency, and SysCtl discoverability are good. Sharp edges: fluent options silently dropped per-driver (WithPlatform, WithIPRange, WithWaitPollInterval), three contradictory port-argument orders, four coexisting error channels (exceptions / CommandResponse / ApiResult / dead Result+Option), documented extension methods unreachable without an undocumented cast (DOC-2/16), and `PodmanMachineNotRunningException` outside the catchable hierarchy (COM-10/DOC-9).
6. **Are docs findable/readable or bloated/fragmented?** Findable and readable — index + learning path give a coherent zero→container→compose→model journey, files respect the 600-line cap, and the model docs are layered rather than fragmented. The one systemic offender is duplication: the Model Runner quick start exists 4× and has already drifted into contradiction (4096 vs 8192 context size, DOC-7).

Traced `Create()…BuildAsync() → RegisterDriverPackAsync → SysCtl<T> → dispose`; simulated concurrent register/dispose, builder reuse, partial-build failure, custom-pack misbehavior. All files under the 500-line rule.

Verdict:
1. Production ready: **NO** — happy path solid and tested, but four Major lifecycle/robustness defects remain; the 54-fix commit hardened registration TOCTOU and partial-build cleanup genuinely but left dispose-vs-register race and builder-reuse aliasing untouched.
2. Docs: **MOSTLY** — one factual error and three omissions (KRN-8); otherwise accurate and current.
3. Zero bugs: **NO** — KRN-1…KRN-9; no test covers concurrent Dispose+Register, builder reuse, or non-conforming custom packs.
4. Resilient: **PARTIALLY** — daemon-down BuildAsync correctly defers health to `IsHealthyAsync`; driver replacement possible but silently leaks the old pack (KRN-3); no kernel-level health/reconnect surface.
5. Easy to consume: **YES**, with one hole (KRN-4: soft-probe guarantee not enforced against custom packs).
6. Docs findable/readable: **YES** — architecture/extensibility sections well-structured and cross-linked.

### Major

- **[KRN-1] Reusing a KernelBuilder aliases one live pack instance across kernels, causing cross-kernel state corruption and use-after-dispose.** `WithDockerCli` instantiates the pack eagerly (`KernelBuilder.cs:37` → `DockerCliDriverBuilder.cs:86`), and `BuildAsync` registers that same stored instance every call (`KernelBuilder.cs:92-101`); nothing marks the builder consumed. A second `BuildAsync()` re-runs `InitializeAsync` on the shared pack, silently replacing kernel A's component drivers and (for `DockerApiDriverPack.cs:72`) leaking the first `DockerApiConnection`; disposing either kernel kills the other's connection (`DockerCliDriverPack.cs:383-392`). Same aliasing hits BuildAsync-failure-then-retry. Smallest fix: instantiate packs inside `BuildAsync` (store a factory), or set a `_built` flag and throw on reuse.

- **[KRN-2] DriverRegistry disposal is not serialized with registration — in-flight RegisterAsync can leak an initialized driver and throw ObjectDisposedException from the semaphore.** `DisposeAsync` (`DriverRegistry.cs:415-454`) never acquires `_registrationLock`, has no Interlocked disposed-guard (violating the repo's own double-dispose rule that `FluentDockerKernel.cs:271` follows), and disposes the semaphore at :451. A registration holding the lock during `InitializeAsync` (`DriverRegistry.cs:80`) completes `TryAdd` after the dispose loop passed — the driver is never disposed — then `finally { _registrationLock.Release(); }` (:103) throws `ObjectDisposedException`. Smallest fix: add the Interlocked guard, take `_registrationLock` in `DisposeAsync`, reject post-dispose registration deterministically.

- **[KRN-3] Unregister removes a driver without disposing it — the documented driver-replacement path silently leaks.** `DriverRegistry.Unregister` (`DriverRegistry.cs:110-122`) drops the registration but the pack (which may own an `HttpClient`, `DockerApiDriverPack.cs:26`) is never disposed, contradicting "registry owns the driver/pack lifecycle" (`FluentDockerKernel.cs:27`). Production services doing Unregister + re-Register (the only dead-driver recovery story) leak per cycle. Smallest fix: dispose (or return) the removed instance and document the ownership contract.

- **[KRN-4] TrySysCtl's soft-probe guarantee can hard-crash with InvalidCastException for custom packs.** The pack path returns `TryResolve` output unvalidated (`FluentDockerKernel.cs:65-66`) while the plain-driver path validates with `IsInstanceOfType` (`FluentDockerKernel.cs:81`). A custom pack returning a wrong-typed instance makes `(T)SysCtl(...)` (`FluentDockerKernel.cs:96`) throw `InvalidCastException`, which `TrySysCtl` (`FluentDockerKernel.cs:108-116`) does not catch. No test covers this. Smallest fix: verify `interfaceType.IsInstanceOfType(resolved)` after pack resolve; throw `InterfaceNotSupportedException` otherwise.

### Minor

- **[KRN-5] DockerCliDriverPack disposal leaves the pack resurrectable.** `DisposeAsync` nulls `_modelInferenceConnection` but not `_modelInferenceDriver` and never resets `_initialized` (`DockerCliDriverPack.cs:383-392`); a retained reference hands out a driver backed by a disposed `HttpClient`, and a later resolve recreates the connection post-dispose (`DockerCliDriverPack.cs:243`) — leaked forever. Double-checked locking uses a non-volatile first read (`DockerCliDriverPack.cs:238`). Fix: dispose-guard flag in `TryGetDriver`, null both fields, `Volatile.Read`.

- **[KRN-6] Missing container binary surfaces as bare `FluentDockerException`, outside the documented driver-error hierarchy.** `DockerBinariesResolver.cs:55` / `PodmanBinariesResolver.cs:44-46` throw `FluentDockerException` from `InitializeAsync`, so no-docker-installed is not catchable as `DriverException`; `DriverNotAvailableException` (`docs/architecture.md:477`) is the type that should fire. Fix: throw `DriverNotAvailableException(driverId, reason)` from pack init.

- **[KRN-7] No detection or documentation of the podman-docker shim.** With `docker` aliased to podman (Fedora podman-docker), the pack reports `RuntimeType.Docker` (`DockerCliDriverPack.cs:64`) and registers Swarm-only stack/service drivers (`DockerCliDriverPack.cs:125-126`) that fail at first use. Fix: one `docker version --format` probe with a warning, or a caveat in `docs/podman.md`.

- **[KRN-8] Doc defects.** (a) Resolution table claims step 2 falls through with "Continue" (`docs/extensibility.md:72`) but code returns/throws terminally (`FluentDockerKernel.cs:69`). (b) Builder single-use nowhere stated (`IKernelBuilder.cs:44-57`). (c) Multiple `AsDefault()` silently last-wins (`KernelBuilder.cs:103-104`). (d) Unregistering the default driver nulls `DefaultDriverId` with no reselection, undocumented (`DriverRegistry.cs:115-121`, `FluentDockerKernel.cs:196-206`). Fix: four one-line doc edits.

- **[KRN-9] A pack that throws mid-InitializeAsync leaks its partially acquired resources.** `RegisterDriverPackAsync` disposes the pack only on the unreachable `TryAdd` failure (`DriverRegistry.cs:200-204`); when `InitializeAsync` throws (`DriverRegistry.cs:188`) nobody disposes the failing instance (e.g. `DockerApiDriverPack` creates its connection at :72 before later init steps). Fix: try/catch around init calling `DisposeDriverPackSafelyAsync`.

- **[KRN-10] Cosmetics.** Kernel `Dispose()` calls `GC.SuppressFinalize` twice (`FluentDockerKernel.cs:288`, `:303`); `SysCtl(null, …)` surfaces a raw `ArgumentNullException` from dictionary internals (`FluentDockerKernel.cs:62`); registry disposal order is unordered dictionary-enumeration order (`DriverRegistry.cs:418, 434`) — harmless today, undocumented.

## Model Runner (DMR) & inference

Examined: all 13 model-scope files in `Services/` + `Impl/` (interfaces + `ModelRunnerService` partials, `ModelService`, `GenericOpenAiModelRunner`); the full inference data plane (`OpenAiModelInferenceDriver` + `.Streaming`, `ModelApiConnection` + `.Tls`, `ModelApiConnectionConfig`, `ModelTlsValidation`, `ResponseOwningStream`); `Common/` gate/env/exception types; value objects (`ModelReference`, `ModelRunnerEndpoint`, `InferenceModelId`); all inference DTOs and Options; builder entry points (`UseModelRunner`/`UseModel`, `ModelRunnerBuilder`, `ModelServiceBuilder`); `DockerCliModelRuntimeDriver`; all four model docs; streaming/gate tests + `MockModelApiConnection`. Ran 160 model unit tests (all pass) and wrote a standalone repro that **deterministically confirms DMR-1**. All files ≤500 lines; one benign `ponytail:` deferral.

Verdict:
1. Production ready: **NO** — one confirmed Critical crash in the SSE hot path (DMR-1) and one Major hang (DMR-2); everything else genuinely well-hardened — one small fix away.
2. Docs: **MOSTLY** — comprehensive and honest, but the error-handling section makes two claims the code contradicts (DMR-4).
3. Zero bugs: **NO** — DMR-1 reproducible mid-stream crash on valid UTF-8; DMR-2 reproducible infinite hang. Prior audit's MR1–MR9 are genuinely fixed (verified, not cosmetic).
4. Resilient: **MOSTLY** — typed errors for restart/refused/DNS; but time-to-first-header unbounded (DMR-2), streaming timeouts not distinguishable from unreachability (DMR-4), no retry guidance in docs.
5. Easy to consume: **YES** — clean `ChatAsync`/`ChatStreamAsync` + DTO escape hatch; `UseModelRunner` vs `UseModel` clearly separated.
6. Docs findable/readable: **YES** — the 4-file split is layered with consistent cross-links, not fragmented.

### Critical

- **[DMR-1] The SSE UTF-8 decode loop overflows its char buffer and crashes the stream with an untyped `ArgumentException` when a multi-byte codepoint spans a full read.** `ReadLinesAsync` allocates `charBuffer = new char[StreamBufferBytes]` (4096) (`OpenAiModelInferenceDriver.Streaming.cs:199`), but a stateful `Decoder` carrying partial-codepoint bytes can emit up to 4097 chars from a 4096-byte read — `decoder.GetChars(...)` (`Streaming.cs:295`) throws `ArgumentException`, reproduced deterministically (emoji split across a boundary + full ASCII read). The exception escapes the `IOException or HttpRequestException` filter (`Streaming.cs:104`) and surfaces raw — killing any long generation containing astral-plane characters (emoji are routine LLM output). Existing framing test uses tiny chunks and cannot hit it. Smallest fix: `new char[Encoding.UTF8.GetMaxCharCount(StreamBufferBytes)]` plus a boundary test.

### Major

- **[DMR-2] The streaming request's header-wait phase is unbounded — a wedged runner hangs `ChatStreamAsync` forever, contradicting the config's own documentation.** `PostStreamAsync` sends with only the caller's token (`ModelApiConnection.cs:155`), `HttpClient.Timeout` is infinite (:69), streaming is exempt from `_requestTimeout` by design (:36-38), and `StreamReadIdleTimeout` guards only body reads *after* the stream opens (`Streaming.cs:87,269-284`). A DMR that accepts TCP but never sends headers — the daemon-restart/wedged scenario — hangs indefinitely for callers without a token, while `ModelApiConnectionConfig.cs:32-33` promises a dead stream "cannot hang forever". Smallest fix: linked CTS with the idle timeout around `SendAsync(ResponseHeadersRead)`.

- **[DMR-3] `ModelOperationGate` coverage is narrower than its contract: direct `IModelRunner.PullAsync`/`LoadAsync`/`UnloadAsync` are ungated.** The gate claims to serialize pull/load/unload on the same model (`ModelOperationGate.cs:10-12`), but `ModelRunnerService.Store.cs:13-19` and `Engine.cs:38-60` never acquire it — only `ModelService` start/stop/dispose, builder pull, and `ConfigureAsync` do. `docs/model-runner.md:89-109` teaches direct `runner.PullAsync` usage, so a documented pattern races exactly what the gate exists to prevent. Smallest fix: move gating into `ModelRunnerService` ops and drop it from `ModelService` (semaphore is non-reentrant — gating both layers would deadlock), or correct the gate's contract docs.

- **[DMR-4] Streaming timeout classification contradicts the `ErrorCodes` contract and the docs, so timeouts are not distinguishable on the streaming path.** `ErrorCodes.ModelInference.Timeout` says the idle window maps to it "so callers can retry/backoff on latency" (`ErrorCodes.cs:311-317`), but streaming maps a fired idle window to `EndpointUnreachable` (`Streaming.cs:275-284`) — same code as connection-refused, opposite retry semantics. `docs/model-runner.md:401` also claims "timeout → `TimeoutException`" when the surface actually throws `ModelRunnerException` MIN_006. Smallest fix: map idle window to `Timeout`, align the three doc sites, add the missing table row.

### Minor

- **[DMR-5] `runner.Endpoint` can still lie under `WithInferenceDriver(...)`.** `ModelRunnerBuilder.cs:143` reports context/default authority while traffic goes wherever the injected driver points (`IModelRunner.cs:20-21`). Fix: document the property as not meaningful under driver override, or add an endpoint to that overload.

- **[DMR-6] The handler-injection `ModelApiConnection` ctor silently drops both streaming and request protections.** The `(Uri, HttpMessageHandler)` overload (`ModelApiConnection.cs:105-122`) leaves idle timeout null and request timeout infinite with no opt-in — the documented custom-transport plugin path inherits hang-forever semantics. Fix: accept a `ModelApiConnectionConfig`.

- **[DMR-7] Build-time pull and configure are not atomic under the gate.** Gate scope closes after pull (`ModelRunnerBuilder.cs:151-156`); `ConfigureAsync` re-acquires separately (:158-159), allowing interleaving on the same model during `BuildAsync`. Fix: widen the `await using` scope.

- **[DMR-8] Streaming chunk DTO models neither `created` nor `usage`; tool calls only ride `AdditionalProperties`.** `ChatStreaming.cs:10-29`, `InferenceCommon.cs:128-133`. Round-trips lossless, but agentic consumers hand-parse JSON. Acceptable for a preview surface; note in known-limitations.

- **[DMR-9] `ModelRunnerEndpoint.Raw`/`Custom` skip the scheme validation the env paths enforce.** `Raw(new Uri("ftp://..."))` builds (`ModelRunnerEndpoint.cs:81-89`) and `CreateTcpHandler` coerces to http (`ModelApiConnection.cs:426-431`) while env paths reject non-http(s) (:180-184,201-204). Fix: call `IsSupportedUrl` in `Raw`/`Custom`.

- **[DMR-10] `PingAsync` counts any HTTP status as reachable, so `GenericOpenAiModelRunner.StatusAsync` reports `Running=true` against a wholly wrong base path.** Ping returns true for 4xx/5xx (`ModelApiConnection.cs:283-288`); `StatusAsync` maps that to `Running` (`GenericOpenAiModelRunner.cs:263-268`). Fix: treat 404 on the model-list probe as not-running with a path hint, or document as reachability.

Positive notes: prior audit's MR1–MR9 substantively fixed (verified in code and tests); `MockModelApiConnection` is genuinely good (byte-level chunk scripting, stalls, mid-stream faults); disposal chains careful and leak-free; model docs among the best-maintained parts of the repo.

## Docker API driver

Examined: every file in `Drivers/Docker/Api/**` (Connection incl. `DockerApiConnection`, `ResponseOwningStream`, config; `DockerApiDriverBase` + ResponseHandling/ErrorHandling/Stream partials; all Components — Container +Operations/CopyFrom/Parsing, Image +Build/BuildContext, Stream, System, Auth, Service, Network, Volume, `DockerApiRegistryAuth`, `DockerIgnoreFilter`, pack; ApiModels + `DockerApiJsonContext`), `Drivers/Models/Connection/**`, `Common/SharedHttpClient.cs`, `JsonHelper.cs`, `RequestResponse.cs`, `docs/docker-api.md`, and ~377 DockerApi unit tests (green on net10.0 locally). Claims were verified empirically, not on faith: (a) `X509Certificate2.CreateFromPemFile(caPath)` throws `CryptographicException` on cert-only ca.pem on net8.0; (b) SharpCompress 0.48.0 `TarWriter.Write` emits all entries as mode 0777; (c) the net8.0 CI leg at HEAD is **red right now** with that exact exception (gh run 28591262723: 4 TLS tests failing). Verified as genuinely correct for balance: X-Registry-Auth base64url matches Go; `ResponseOwningStream` disposal idempotent; `EnsureStreamSuccessAsync` disposes on all failure paths; TLS name-mismatch still rejected; archive path-traversal guard works; DockerIgnore last-match-wins/negation works.

Verdict:
1. Production ready: **NO on net8.0** (TLS-with-CA crashes at construction — CI net8 leg red at HEAD); **conditionally on net10.0** — transport/disposal/error taxonomy solid, but follow-logs, attach/exec stdin, and 0777 build contexts are shipping footguns.
2. Docs: **MOSTLY** — concise single page, but two factual claims the code contradicts (frame errors; timeout distinctness) and omits legacy-builder/symlink divergences.
3. Zero bugs: **NO** — 2 Critical, 7 Major, ~18 Minor; the "54 issues ALL fixed" claim is disproven by the repo's own CI (net8 leg fails on tests the hardening commit added; "4155 unit pass" was net10 only).
4. Resilient: **PARTIALLY** — false-success hardening real, but streams truncate silently on malformed frames, `WaitAsync` misdiagnoses long waits as "daemon unreachable", Pull/Push leak raw `TaskCanceledException`.
5. Easy to consume: **YES** — consistent `CommandResponse<T>`, fluent config, good XML docs; marred by advertised-but-unimplemented stdin.
6. Docs findable/readable: **YES** — single 143-line page, not bloated.

### Critical

- **[API-1] TLS with a custom CA is completely broken on net8.0 — the connection constructor throws before any request, and CI has been red on this since the hardening commit.** `DockerApiConnection.cs:419` and `ModelApiConnection.cs:480` (`#else` of `#if NET9_0_OR_GREATER`) call `X509Certificate2.CreateFromPemFile(caPath)`, which requires a private key; ca.pem is cert-only → `CryptographicException` — empirically reproduced and confirmed in CI run 28591262723 (net8.0 ubuntu, 4 tests). The documented `WithCertificates("/etc/docker/certs")` setup crashes for every net8.0 tcp+TLS consumer. Smallest fix: `X509Certificate2.CreateFromPem(File.ReadAllText(caPath))` in both `#else` branches.

- **[API-2] `GetLogsAsync(follow: true)` buffers the entire log stream into a `MemoryStream` and never returns for a running container.** `DockerApiContainerDriver.Operations.cs:42-45` does `CopyToAsync` into memory before demultiplexing; with follow the body stays open indefinitely and `RequestTimeout` doesn't apply after headers (ResponseHeadersRead) — unbounded memory + hang until caller cancellation or container exit. Smallest fix: reject `follow=true` on this buffered API (direct callers to `IStreamDriver.StreamLogsAsync`) or demultiplex incrementally.

### Major

- **[API-3] Build-context tar writes every file as mode 0777, silently diverging from `docker build` CLI semantics.** `DockerApiImageDriver.BuildContext.cs:53-54` uses SharpCompress `writer.Write(name, stream, date)` which (empirically proven on 0.48.0) emits all entries `-rwxrwxrwx`; same pattern in `CopyToContainerAsync` (`Operations.cs:322,360`). COPY'd private keys/configs land world-writable — sshd/postgres reject them, failing only at container runtime. Smallest fix: construct `TarEntry` headers with the source Unix mode (or 0644/0755 split).

- **[API-4] Malformed or oversized multiplexed frames silently truncate streams, and the docs claim the opposite.** `DockerApiStreamDriver.cs:359` `yield break`s on bad frame size; `StripDockerStreamHeaders` (`DockerApiDriverBase.Stream.cs:195,216`) breaks and drops the remainder — but `docs/docker-api.md:120-124` states "a partial or oversized frame throws a DriverException". Audit/compliance log consumers get silent data loss. Smallest fix: throw on invalid frame headers (making docs true), or fix docs + log a warning.

- **[API-5] `WaitAsync` is silently capped by the 5-minute `RequestTimeout` and then misreports "Cannot connect to Docker daemon" (503).** `DockerApiContainerDriver.cs:178-198` long-polls via buffered `PostJsonAsync` governed by `HttpClient.Timeout`; on expiry `IsConnectionError` (`ErrorHandling.cs:56-62`) maps the internal `TaskCanceledException` to a connection failure while the daemon is healthy. Smallest fix: per-request infinite timeout honoring only the caller's token, like the streaming endpoints.

- **[API-6] Pull/Push let internal timeouts escape as raw `TaskCanceledException`, contradicting the documented error taxonomy.** `DockerApiImageDriver.Build.cs:79` (pull), `:166` (push) catch only `HttpRequestException`; timeout cancellations bypass `IsConnectionError` mapping, so callers see what looks like their own cancellation — precisely on flaky-network pulls (`docs/docker-api.md:67-77` promises distinct failure modes). Smallest fix: add the `catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested)` mapping used by the JSON helpers.

- **[API-7] The "symlink escape fixed via realpath canonicalization" (373be16) is check-then-use: TOCTOU-racy, and on Windows silently degrades to a lexical check.** `BuildContext.cs:165-188` resolves the target at enumeration time but opens the original path at `:53`; target swappable between check and open; `:203` carries a `ponytail:` comment admitting Windows is "best-effort — lexical only". Real improvement, but "closed" is overstated for hostile contexts (shared temp dirs, CI runners). Smallest fix: open the FileStream first, verify containment on the opened handle's resolved path.

- **[API-8] Interactive stdin for exec/attach is advertised by the API surface but not implemented — consumers get a null `InputStream` and hung processes.** `AttachResult` documents `InputStream` (`IStreamDriver.cs:311-312`), `ExecAsync` sets `AttachStdin` (`Operations.cs:160`), `AttachAsync` sends the stdin query param (`DockerApiStreamDriver.cs:247-267`) — but no HTTP hijacking exists; `InputStream` never populated; `ErrorStream` null while `OutputStream` carries raw multiplexed bytes. Commands reading stdin block forever with no error. Smallest fix: throw `FluentDockerException` when stdin is requested; document the limitation.

- **[API-9] Swarm service IDs and query values are interpolated into URLs without escaping — the only driver family that skips `Uri.EscapeDataString`.** `DockerApiServiceDriver.cs:48,72,92,138,177` build `/services/{serviceId}` raw; `:183` appends `config.Since` unescaped. A name containing `/`, `?`, `#` redirects the request — path injection against the daemon socket. Smallest fix: escape every interpolated segment, matching sibling drivers.

### Minor

- **[API-10] Named-pipe `ConnectCallback` leaks the pipe stream if `ConnectAsync` throws.** `DockerApiConnection.cs:362-367` — unix branch wraps in try/dispose, npipe branch doesn't. Fix: mirror it.
- **[API-11] Stale comment contradicts adjacent code.** `DockerApiDriverBase.cs:260-261` says "leaveOpen:false (default) will dispose" beside `leaveOpen: true`. Fix: correct comment.
- **[API-12] `ConfigureAwait(false)` — an AGENTS.md hard rule — missing on several awaits.** `DockerApiDriverBase.Stream.cs:237`, `DockerApiContainerDriver.cs:35-39`, `Operations.cs:170-174,223-225`. Deadlock risk under a sync context. Fix: add suffix.
