## (3) Resolving a driver port (component) from the kernel by `driverId` — exact pattern

### The SysCtl call signature
`FluentDocker/Kernel/ISysCtl.cs` (implemented by `FluentDockerKernel`):
```csharp

```
`FluentDockerKernel.SysCtl<T>` impl (`FluentDocker/Kernel/FluentDockerKernel.cs:94`):
```csharp
public T SysCtl<T>(string driverId) where T : class => (T)SysCtl(driverId, typeof(T));
```

### The exact idiom every service uses (copy verbatim)
Inside each operation method a service resolves its driver "port" then builds a `DriverContext`:
```csharp
var driver  = _kernel.SysCtl<IContainerDriver>(_driverId);   // ContainerService.cs:117 (and ~20 more call sites)
var context = new DriverContext(_driverId);                  // ContainerService.cs:118
```
`VolumeService.cs:65` uses the identical pattern with `IVolumeDriver`:
```csharp
var driver  = _kernel.SysCtl<IVolumeDriver>(_driverId);
var context = new DriverContext(_driverId);
```
So for `ModelRunnerService`/`ModelService` you call `_kernel.SysCtl<IModelDriver>(_driverId)` (your new driver-component interface) and `new DriverContext(_driverId)`.

`DriverContext` (`FluentDocker/Model/Drivers/DriverContext.cs`): ctor `DriverContext(string driverId)` at line 115 sets `DriverId`; `LoggerFactory` defaults to `NullLoggerFactory.Instance`. The service does NOT populate Host/Sudo/etc. — it just passes the driverId; the registry/pack already holds the connection config.

### The exception thrown when the interface is unsupported
`FluentDockerKernel.SysCtl(string, Type)` (`FluentDockerKernel.cs:57-88`) resolution order: driver pack `TryResolve` → pack `SysCtl` → regular-driver `IDriverInterfaceResolver.TryResolve` → direct cast. On failure:
```csharp
throw new InterfaceNotSupportedException(driverId, interfaceType.Name);  // line 84  (driver exists, no such interface)
throw new DriverNotFoundException(driverId);                              // line 87  (no such driverId)
```
- `InterfaceNotSupportedException` — `FluentDocker/Common/InterfaceNotSupportedException.cs:9`, extends `DriverException`, ctor `(string driverId, string interfaceName)`, props `DriverId`/`InterfaceName`, error code `ErrorCodes.Driver.InterfaceNotSupported`.
- `DriverNotFoundException` — `FluentDocker/Common/DriverNotFoundException.cs:9`, extends `DriverException`, ctor `(string driverId)`, error code `ErrorCodes.Driver.NotFound`.

### Where `InterfaceNotSupportedException` is CAUGHT (capability-probe pattern)
`FluentDockerKernel.TrySysCtl<T>` (`FluentDockerKernel.cs:103-119`) is the only catcher:
```csharp
public bool TrySysCtl<T>(string driverId, out T instance) where T : class {
  ThrowIfDisposed();
  instance = null;
  try { instance = SysCtl<T>(driverId); return true; }
  catch (InterfaceNotSupportedException) { return false; }
  // DriverNotFoundException intentionally propagates — a missing driver is a hard error
}
```
Use `_kernel.TrySysCtl<IModelDriver>(_driverId, out var modelDriver)` in `ModelRunnerService` if you want graceful "this driver doesn't support model running" behavior instead of a throw. Note: no service in `Services/` currently calls `TrySysCtl` — they all call the throwing `SysCtl<T>` directly. Other drivers also throw `InterfaceNotSupportedException` from their own pack resolvers (`DriverPackBase.cs:53`, `DockerCliDriverPack.cs:156/185`, `DockerApiDriverPack.cs:145/154`, `PodmanCliDriverPack.cs:163/192`).

## (4) How `CommandResponse<T>` failures become exceptions (the translation helper)

There is NO shared helper method — translation is INLINED at every call site as an `if (!response.Success) throw ...` block. The canonical form (`VolumeService.cs:70-76`):
```csharp
var response = await driver.InspectAsync(context, _volumeName, cancellationToken).ConfigureAwait(false);
if (!response.Success)
{
  throw new DriverException(
      $"Failed to inspect volume '{_volumeName}': {response.Error}",
      response.ErrorCode,
      response.ErrorContext);
}
return response.Data;
```
`CommandResponse<T>` (`FluentDocker/Model/Drivers/CommandResponse.cs`) members (all `init`-only): `bool Success` (16), `T Data` (21), `string Error` (26), `string ErrorCode` (31), `ErrorContext ErrorContext` (36), `int ExitCode` (41), `string Output` (46). Factories: `Ok(T)`, `Ok(T,string)`, `Fail(string error, string errorCode=null, int exitCode=-1)`, `Fail(string,string,ErrorContext,int)`.

`DriverException` (`FluentDocker/Common/DriverException.cs:9`, base `FluentDockerException`) ctor overloads used:
- `DriverException(string message, string errorCode)` — line 37 (when no context, e.g. `ContainerService.Operations.cs:27`).
- `DriverException(string message, string errorCode, ErrorContext context, bool isTransient=false)` — line 59 (the 3-arg form used by VolumeService/ContainerService Inspect/Remove/Pause/Stop).
Props: `string ErrorCode`, `ErrorContext Context`, `bool IsTransient`.

Two translation conventions to mirror:
- **Generic failures** → `DriverException(msg, response.ErrorCode, response.ErrorContext)` (Inspect/Pause/Stop/Kill/Remove). See `ContainerService.cs:149-153, 171-175, 193-197, 217-221, 251-255` and `VolumeService.cs:72-76, 105-109`.
- **Start failures** → a specialized subclass `ContainerStartException(_containerId, response.Error, response.ErrorContext)` (`ContainerService.cs:127-131`). `ContainerStartException` (`FluentDocker/Common/ContainerStartException.cs:9`) extends `DriverException`, error code `ErrorCodes.Container.StartFailed`, `isTransient: true`. For `ModelService` you may define a parallel `ModelStartException` or just use `DriverException`.
- Operations-file failures pass only `(message, response.ErrorCode)` — no context — e.g. `ContainerService.Operations.cs:27-30, 49-52, 70-73`.

Message format convention: `$"Failed to <verb> <resource> '{_name}': {response.Error}"`.

## (5) State-transition + hook firing pattern in `ContainerService`

Files: `FluentDocker/Services/Impl/ContainerService.cs` (464 lines, main: lifecycle + hooks + dispose) and `ContainerService.Operations.cs` (260 lines, exec/copy/logs/stats/port). Class is `public partial class ContainerService : IContainerService, IServiceCapabilities` (line 21).

### Two-layer hook system
There are TWO hook collections (ContainerService.cs:35-37):
1. `Dictionary<string, Func<IServiceAsync, Task>> _hooks` — keyed by uniqueName (for removal).
2. `Dictionary<ServiceRunningState, List<Func<IServiceAsync,Task>>> _stateHooks` — keyed by state, populated for every enum value in the ctor (`ContainerService.cs:92-95`):
   ```csharp
   foreach (var state in Enum.GetValues<ServiceRunningState>()) _stateHooks[state] = [];
   ```
`AddHook` (line 286) writes to BOTH dicts; `RemoveHook` (line 294) removes from `_hooks` and scrubs the same delegate from all `_stateHooks` lists.
(VolumeService uses a SIMPLER single `_hooks` dict + iterates all values regardless of state — `VolumeService.cs:31, 115-126, 167-180`. For a single-resource `ModelService`, the simpler VolumeService model is sufficient; copy the two-dict model only if you need per-state hooks like ContainerService.)

### The transition + firing sequence (StartAsync, ContainerService.cs:115-138 — the template)
```csharp
public async Task StartAsync(CancellationToken cancellationToken = default)
{
  var driver  = _kernel.SysCtl<IContainerDriver>(_driverId);
  var context = new DriverContext(_driverId);

  UpdateState(ServiceRunningState.Starting);                              // 1. transition to *-ing FIRST
  await ExecuteHooksAsync(ServiceRunningState.Starting).ConfigureAwait(false);  // 2. fire hooks for that state

  var response = await driver.StartAsync(context, _containerId, cancellationToken).ConfigureAwait(false);  // 3. driver call
  if (!response.Success)
    throw new ContainerStartException(_containerId, response.Error, response.ErrorContext);  // 4. translate failure (state stays Starting)

  UpdateState(ServiceRunningState.Running);                              // 5. transition to terminal state
  await ExecuteHooksAsync(ServiceRunningState.Running).ConfigureAwait(false);  // 6. fire terminal-state hooks
}
```
Order invariant for ALL ops: `UpdateState(transient) → ExecuteHooks(transient) → driver call → throw-on-failure → UpdateState(final) → ExecuteHooks(final)`.
- `StopAsync` (159-179): Stopping→hooks→`driver.StopAsync(context,_containerId,null,ct)`→Stopped→hooks.
- `PauseAsync` (140-157): no transient state, just `driver.PauseAsync`→Paused→hooks.
- `KillAsync` (181-201): Stopping→hooks→`driver.KillAsync(...,signal,...)`→Stopped→hooks.
- `RemoveAsync` (203-225): Removing→`ExecuteHooksAsync(Removing)`→`ExecuteLifecycleHooksAsync(Removing, ct)`→driver remove→Removed→hooks. (Lifecycle hooks are an EXTRA pipeline distinct from state hooks — `_lifecycleHooks` list, CopyTo/CopyFrom/Export/Execute, ContainerService.cs:387-448; you likely don't need this for ModelService.)

### `UpdateState` — the single mutation + event-raise point
ContainerService (`ContainerService.cs:361-367`):
```csharp
private void UpdateState(ServiceRunningState newState)
{
  var oldState = _state;
  _state = newState;
  InvalidateInspectCache();                                              // see §inspect cache
  StateChange?.Invoke(this, new StateChangeEventArgs(this, newState));
}
```
VolumeService variant (no cache, `VolumeService.cs:161-165`): `_state = newState; StateChange?.Invoke(this, new StateChangeEventArgs(this, newState));`

### `ExecuteHooksAsync` — swallows hook exceptions
ContainerService (`ContainerService.cs:369-385`):
```csharp
private async Task ExecuteHooksAsync(ServiceRunningState state)
{
  if (!_stateHooks.TryGetValue(state, out var hooks)) return;
  foreach (var hook in hooks)
  {
    try { await hook(this).ConfigureAwait(false); }
    catch (Exception ex) { _logger.LogError(ex, "ContainerService hook execution failed"); }  // never rethrows
  }
}
```
Hooks must NEVER break the lifecycle — exceptions are logged and swallowed.

## (6) `IAsyncDisposable` usage (the exact dual-dispose idiom)

Both services use an `Interlocked`-guarded shared `DisposeCoreAsync()`. Backing field `private int _disposed;` (ContainerService.cs:311, VolumeService.cs:128).

VolumeService (`VolumeService.cs:128-159`) — minimal template for ModelService:
```csharp
private int _disposed;

public void Dispose()
{
  if (Interlocked.CompareExchange(ref _disposed, 1, 0) != 0) return;
  DisposeCoreAsync().AsTask().GetAwaiter().GetResult();      // sync bridges to async core
  GC.SuppressFinalize(this);
}

public async ValueTask DisposeAsync()
{
  if (Interlocked.CompareExchange(ref _disposed, 1, 0) != 0) return;
  await DisposeCoreAsync().ConfigureAwait(false);
  GC.SuppressFinalize(this);
}

private async ValueTask DisposeCoreAsync()
{
  if (!_removeOnDispose) return;
  try { await RemoveAsync(force: true).ConfigureAwait(false); }
  catch (Exception ex) { _logger.LogWarning(ex, "VolumeService DisposeAsync failed"); }  // swallow
}
```
ContainerService variant (`ContainerService.cs:311-355`): same guard, but `DisposeCoreAsync` first conditionally `StopAsync()` (if `_stopOnDispose` && state is Running/Paused) then conditionally `RemoveAsync(force:true)` (if `_deleteOnDispose`), each in its own try/catch that logs a warning and continues. Disposal cleanup MUST swallow exceptions.

Key rules: `Dispose()` delegates to async core via `.AsTask().GetAwaiter().GetResult()`; both paths idempotent via `Interlocked.CompareExchange(ref _disposed, 1, 0) != 0` early-return; both call `GC.SuppressFinalize(this)`.
