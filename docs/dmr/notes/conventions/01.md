## 2. ExecuteCommandAsync — EXACT signatures & behavior
File: `DockerCliDriverBase.cs`. Return type is ALWAYS `Task<SimpleCommandResult>`.

Three overloads (all `protected async Task<SimpleCommandResult>`):
```csharp
// line 139
ExecuteCommandAsync(string arguments, CancellationToken cancellationToken)
// line 150 — pipes stdinData to the process stdin
ExecuteCommandAsync(string arguments, string stdinData, CancellationToken cancellationToken)
// line 162 — adds extra env vars
ExecuteCommandAsync(string arguments, IDictionary<string,string> environment, CancellationToken cancellationToken)
```
Internal flow (line 141-144): resolves `(binaryPath, sudo, sudoPassword)` via `ResolveBinaryInfo()`, prepends global args via `BuildGlobalArgs(Context)`, then `ExecuteProcessAsync(...)`.

`SimpleCommandResult` (line 474-495) — the return DTO, mutable get/set:
```csharp
public class SimpleCommandResult {
  public bool   Success  { get; set; }  // == (ExitCode == 0)
  public string Output   { get; set; }  // full stdout (UTF-8, ReadToEndAsync)
  public string Error    { get; set; }  // full stderr (UTF-8)
  public int    ExitCode { get; set; }
}
```
ExecuteProcessAsync behavior (line 179-270), important guarantees:
- `Success = (process.ExitCode == 0)` (line 245). On caught exception returns `{Success=false, Error=ex.Message, ExitCode=-1}` (line 259-264) — it does NOT throw for normal failures; only `OperationCanceledException` is rethrown (after killing the child, line 251-256).
- stdout + stderr read CONCURRENTLY (line 234-238) to avoid pipe-buffer deadlock; encoding forced UTF-8 (line 207-208).
- `UseShellExecute=false`, `CreateNoWindow=true`. Arguments are passed as a single `Arguments` string — there is NO array-arg API, hence quoting is the caller's responsibility (see §3).

Adapter pattern: always `var result = await ExecuteCommandAsync(args, cancellationToken).ConfigureAwait(false);` then branch on `result.Success`.

## 3. QuoteArgumentIfNeeded — signature & escaping (SECURITY-CRITICAL)
File: `DockerCliDriverBase.cs:455`.
```csharp
protected static string QuoteArgumentIfNeeded(string argument)
```
Behavior (line 455-466):
- `null` or empty -> returns the literal two-char string `"\"\""` (i.e. `""`), NOT null.
- Quoting triggered when the arg contains ANY shell metacharacter from the SearchValues set (line 448-449): space, tab, `;`, `&`, `|`, `>`, `<`, `"`, `'`, `$`, backtick, `!`, `*`, `?`. Membership test: `argument.AsSpan().IndexOfAny(ShellMetaCharacters) >= 0`.
- If no metachar -> returns the argument UNCHANGED (unquoted). So plain tokens like `nginx:latest` pass through verbatim.
- When quoting: escapes backslashes first then double-quotes: `argument.Replace("\\", "\\\\").Replace("\"", "\\\"")`, then wraps in `"..."`. Resulting form: `"{escaped}"`.

Security-test implications: an input containing `;`, `&&`, `$(...)`, backticks, `|`, `>` etc. WILL be quoted and the metachars neutralized (the whole thing becomes a single quoted token, no shell because `UseShellExecute=false`). Inputs WITHOUT metachars are NOT quoted — fine since no shell is involved, but injection of a leading `-` (flag injection) is NOT handled by this method; use `--` separators where the CLI supports them if you need that. Note: `=` and `-`, `/`, `:`, `.`, `@` are NOT in the metachar set, so `key=value`, paths, image refs pass unquoted unless they also contain a metachar.

It is `static` and `protected` — directly callable from any derived adapter. New adapters MUST route every user-supplied value (names, filters, labels, ids, paths used as args) through it, matching existing usage e.g. `DockerCliVolumeDriver.cs:39,44,50,53,87,121,126,174` and `DockerCliImageDriver.cs:41,69,102,...`.

Other quoting idioms seen: format strings quoted inline as literals `--format "{{json .}}"` (volume ls line 116, image list line 208, stream line 75/112). Output file paths sometimes quoted manually with `\"{outputPath}\"` instead of QuoteArgumentIfNeeded (image Save line 139, Load line 166, Import line 217-218) — prefer QuoteArgumentIfNeeded for new code for consistency/safety.

## 4. Building a command string & mapping to CommandResponse + CreateErrorContext
Two build idioms:
- List<string> + join (volume Create `DockerCliVolumeDriver.cs:36-55`, image Build `DockerCliImageDriver.cs:99-136`): `var args = new List<string>{ "volume","create" }; ... args.Add($"--driver {QuoteArgumentIfNeeded(...)}"); ... ExecuteCommandAsync(string.Join(" ", args), ct)`.
- String concat (volume Remove `:84-87`, image Remove `Operations.cs:55-60`, stream BuildStreamLogsArgs `:37-50`): `var args = "volume rm"; if(force) args += " --force"; args += $" {QuoteArgumentIfNeeded(name)}";`.

CommandResponse mapping (`Model/Drivers/CommandResponse.cs`). `CommandResponse<T>` has init-only props: `Success, Data, Error, ErrorCode, ErrorContext, ExitCode, Output`. Factory methods:
```csharp
CommandResponse<T>.Ok(T data)                                   // line 51, ExitCode=0
CommandResponse<T>.Ok(T data, string output)                    // line 64
CommandResponse<T>.Fail(string error, string errorCode=null, int exitCode=-1)        // line 78
CommandResponse<T>.Fail(string error, string errorCode, ErrorContext context, int exitCode=-1)  // line 92
```
Canonical adapter method skeleton (copy verbatim — from volume/image drivers):
```csharp
public async Task<CommandResponse<TResult>> XxxAsync(
    DriverContext context, /* params */, CancellationToken cancellationToken = default)
{
  try
  {
    var args = /* build */;
    var result = await ExecuteCommandAsync(args, cancellationToken).ConfigureAwait(false);
    if (!result.Success)
    {
      return CommandResponse<TResult>.Fail(
          result.Error ?? "Xxx failed",
          ErrorCodes.Area.XxxFailed,
          CreateErrorContext(context, "OperationName", result),
          result.ExitCode);
    }
    return CommandResponse<TResult>.Ok(/* parsed Data */);
  }
  catch (Exception ex)
  {
    return CommandResponse<TResult>.Fail(ex.Message, ErrorCodes.Area.XxxFailed);
  }
}
```
Notes on conventions:
- The OUTER try/catch returns a 2-arg `Fail(ex.Message, errorCode)` (no ErrorContext) — exit code defaults to -1.
- The `!result.Success` branch uses `result.Error ?? "<fallback>"` and the 4-arg `Fail(...)` WITH `CreateErrorContext` and `result.ExitCode`. Some methods (image Tag `Operations.cs:32`, Remove `:66`, Pull-fail `DockerCliImageDriver.cs:45`) omit the ErrorContext (use 2-arg Fail) — both are accepted in the codebase, but prefer the 4-arg with context for new management/runtime ops.
- For `Unit` results (no payload) return `CommandResponse<Unit>.Ok(Unit.Default)` (volume Remove `:100`). `Unit` is from `FluentDocker.Common`.

CreateErrorContext helpers (`DockerCliDriverBase.cs`):
```csharp
// line 382 (static)
protected static ErrorContext CreateErrorContext(DriverContext context, string operation, SimpleCommandResult result)
// line 400 (instance, uses this.Context)
protected ErrorContext CreateErrorContext(string operation, SimpleCommandResult result)
```
The static one maps: `new ErrorContext(operation){ DriverId=context.DriverId, Host=context.Host, ExitCode=result.ExitCode, StdOut=result.Output, StdErr=result.Error }` (line 384-391). Existing adapters call the STATIC overload passing the method's `context` param: `CreateErrorContext(context, "CreateVolume", result)` — DO THIS (the param `context` is the per-call DriverContext, distinct from the field `Context`). `ErrorContext` (`Model/Drivers/ErrorContext.cs`) also has `OperationId`, `Operation`, `Metadata`, `Timestamp` (auto UtcNow) but CreateErrorContext does not populate OperationId.

ErrorCodes: referenced as `ErrorCodes.Volume.CreateFailed`, `ErrorCodes.Image.PullFailed`, `ErrorCodes.General.Unknown`, `ErrorCodes.Container.AttachFailed`, etc. (from `FluentDocker.Common`). Pick/add the matching area+name.

## 5. Streaming-stdout mechanism — ALREADY EXISTS (do NOT add)
File: `DockerCliDriverBase.cs:278`. There IS a built-in streaming primitive:
```csharp
protected async IAsyncEnumerable<string> ExecuteStreamingCommandAsync(
    string arguments, [EnumeratorCancellation] CancellationToken cancellationToken)
```
Behavior (line 278-328): resolves binary + global args + sudo (sudo via stdin password only, NoPassword/Password handled), starts process with redirected stdout, loops `reader.ReadLineAsync(cancellationToken)` yielding each line until null or cancellation; `finally` calls `KillProcessSafely(process, Logger)` (line 326) to avoid orphans. It does NOT capture/return stderr or exit code — line-oriented stdout only. Sudo with Password writes the password line then closes stdin (line 305-309); it does NOT support piping additional stdin data while streaming.

How adapters consume it (`DockerCliStreamDriver.cs`):
```csharp
public async IAsyncEnumerable<string> StreamLogsAsync(DriverContext context, string containerId,
    StreamLogsConfig config=null, [EnumeratorCancellation] CancellationToken ct=default)
{
  var args = BuildStreamLogsArgs(containerId, config);
  await foreach (var line in ExecuteStreamingCommandAsync(args, ct))
    yield return line;            // line 63-66
}
```
For JSON-per-line streams, deserialize inside the loop and swallow parse errors with `Logger.LogDebug` (events `:86-101`, stats `:131-145`). ANSI-prefix handling for `docker stats` streaming is done in `ParseStreamStatsLine` (`:156-212`) by slicing `json.IndexOf('{')`..`LastIndexOf('}')` — reuse this approach if your stream emits cursor escape codes.

IMPORTANT: the IMAGE PULL path does NOT stream. `DockerCliImageDriver.PullAsync` (`DockerCliImageDriver.cs:31-58`) runs a normal blocking `ExecuteCommandAsync("pull ...")` and IGNORES the `IProgress<ImagePullProgress> progress` parameter entirely — no per-line progress is parsed. So there is currently NO streaming-progress mechanism for pull/push/build; if your NEW adapter needs incremental progress callbacks you must build it yourself on top of `ExecuteStreamingCommandAsync` (parse each line into a progress event and call `progress?.Report(...)`). The base class already gives you the line stream; you only add the parsing/Report layer.

Two other process primitives exist for long-running attach (not line streaming):
- `protected AttachResult ExecuteAttachProcess(string arguments)` (line 333) — returns raw `InputStream/OutputStream/ErrorStream` + `AttachedProcess`; sudo-with-password NOT supported (passes null, line 341). Used by `DockerCliStreamDriver.AttachAsync` (`:233`) which wraps it synchronously in `Task.FromResult(CommandResponse<AttachResult>.Ok(result))`.

## 6. How sudo / binary path are threaded
Private resolver (`DockerCliDriverBase.cs:124-131`):
```csharp
private (string BinaryPath, SudoMechanism Sudo, string SudoPassword) ResolveBinaryInfo()
{
  if (BinaryResolver == null) return (DockerCommand, SudoMechanism.None, null); // literal "docker"
  var binary = BinaryResolver.Resolve(DockerCommand);
  return (binary.FqPath, binary.Sudo, binary.SudoPassword);
}
```
So binary path comes from `DockerBinary.FqPath` (= `Path.Combine(Path, Binary)`, `DockerBinary.cs:73`) and sudo config comes from the same `DockerBinary`. Adapters NEVER touch this directly — they just call `ExecuteCommandAsync`/`ExecuteStreamingCommandAsync` and it is threaded automatically.

Sudo execution (`DockerCliDriverBase.cs:414-423`) — password NEVER on command line:
```csharp
private static (string FileName, string Arguments, string PasswordForStdin) BuildSudoCommand(
    string binaryPath, string arguments, SudoMechanism sudo, string sudoPassword)
=> sudo switch {
    SudoMechanism.NoPassword => ("sudo", $"{binaryPath} {arguments}", null),
    SudoMechanism.Password   => ("sudo", $"-S {binaryPath} {arguments}", sudoPassword),
    _                        => (binaryPath, arguments, null) };
```
Password is written to stdin (`process.StandardInput.WriteLineAsync(passwordForStdin)`, line 224/307). `SudoMechanism` enum (from `FluentDocker.Model.Common`) values: `None`, `NoPassword`, `Password`.

Binary resolution chain (`Binary/`):
- `IBinaryResolver` (`IBinaryResolver.cs`): props `DockerBinary[] Binaries`, `MainDockerClient`, `MainDockerCompose`, `MainDockerCli`, `bool IsDockerComposeAvailable`; methods `DockerBinary Resolve(string binary)` and `string ResolveBinaryPath(string dockerCommand)`.
- `DockerBinariesResolver` (`DockerBinariesResolver.cs`) ctors: `(BinaryConfiguration, ILoggerFactory=null)` (line 35) and `(SudoMechanism, string password, params string[] paths)` (line 68). `Resolve("docker")` maps `DockerBinaryType.DockerClient -> MainDockerClient` (line 94-107); throws `FluentDockerException` if not found. `ResolveBinaryPath` prepends `sudo`/`sudo -S` EXCEPT on Windows or `SudoMechanism.None` (line 115-125) — but note the BASE class does NOT use `ResolveBinaryPath`; it uses `Resolve(...).FqPath` + its own `BuildSudoCommand`, so sudo prefixing happens in the base, not the resolver, for command execution.
- The pack builds the resolver from `DriverContext` (`DockerCliDriverPack.cs:61-69`): `BinaryConfiguration { Sudo=context.Sudo, SudoPassword=context.SudoPassword, DefaultShell=context.DefaultShell, BinaryName = context.BinaryName ?? "docker", SearchPaths=context.SearchPaths }`. Custom engine support (finch/nerdctl) flows through `BinaryName`; the resolved binary is still typed `DockerClient` so `Resolve("docker")` returns it (`DockerBinariesResolver.cs:143-146`, 178-181).
- `DockerBinary.Translate` (`DockerBinary.cs:57-68`) only knows `docker`/`docker.exe`, `dockercli`/`.exe`, `compose`; throws `ArgumentException` otherwise. Docker Machine/Toolbox/standalone docker-compose removed in v3.

Global flags threading: `BuildGlobalArgs(DriverContext)` (`DockerCliDriverBase.cs:90-114`, public static) emits `-H {Host}` and TLS flags (`--tlsverify`/`--tls`, `--tlscacert/--tlscert/--tlskey` from `CertificatePath`+ca.pem/cert.pem/key.pem) and is auto-prepended to args inside every Execute* method (line 142-143, 281-282, 336-337). Returns "" when Context null or Host empty. Adapters do not call this.

## 7. DriverContext usage in adapter methods
`DriverContext` (`Model/Drivers/DriverContext.cs`) is passed as the FIRST parameter to EVERY public adapter method (matching the driver interfaces). There are TWO DriverContext references in play:
- The METHOD PARAMETER `context` — pass this to `CreateErrorContext(context, "Op", result)`. This is the per-operation context (carries `DriverId`, `Host`, `OperationId`, `Metadata`).
- The FIELD `Context` (capital C, `DockerCliDriverBase.cs:31`) — set during `Initialize`, used internally by Execute* for `BuildGlobalArgs(Context)`. Adapters normally do NOT read the field directly; they receive `context` as a param. In existing components the param and the field are the same instance (pack passes one context), but the convention is: USE THE PARAMETER for error context.

Key `DriverContext` fields adapters may read off the param: `DriverId`, `Host`, `CertificatePath`, `VerifyTls`, `OperationId`, `Metadata`, `Sudo`/`SudoPassword`/`DefaultShell` (already consumed by resolver), `BinaryName`, `SearchPaths`, `ConnectionTimeout`/`RequestTimeout`/`ApiVersion` (API-driver only — irrelevant to CLI adapters), `LoggerFactory`. `LoggerFactory` defaults to `NullLoggerFactory.Instance`.

Interface method signature convention (e.g. `IVolumeDriver` in `FluentDocker/Drivers/IVolumeDriver.cs:13`): all return `Task<CommandResponse<T>>`, first param `DriverContext context`, last param `CancellationToken cancellationToken = default`. Streaming methods return `IAsyncEnumerable<T>` with `[EnumeratorCancellation] CancellationToken cancellationToken = default` (see `IStreamDriver`).
