# AREA: FluentDocker Compose builder: YAML modeling/emit, attach-to-existing parse path, and where a top-level `models:` + per-service `models:` binding would slot in

## Executive summary (READ FIRST — affects the whole Phase 7b design)

**There is NO YAML serializer in this repo, and the v3.1 "compose builder" does NOT emit YAML at all.** Two separate, *disconnected* worlds exist:

1. **A POCO compose model** (`FluentDocker/Model/Compose/*.cs`) + a fluent **`ComposeServiceBuilder`** (`FluentDocker/Builders/ComposeServiceBuilder.cs`) that *populate a `ComposeServiceDefinition` object graph in memory*. **These are orphaned scaffolding** — `ComposeServiceBuilder` has an `internal` ctor (`ComposeServiceBuilder.cs:21`) and is referenced **nowhere** outside its own file (verified by repo-wide grep). There is no code that turns a `ComposeServiceDefinition` into YAML text. No `ToYaml`, no `ISerializer`, no template engine, no `services:`-emitting code exists anywhere in `FluentDocker/`.

2. **The actual v3.1 compose pipeline** (`IComposeBuilder` → `ComposeBuilder` → `IComposeDriver`/`DockerCliComposeDriver`) is **purely file-path + CLI-flag based**. It never reads or writes YAML *content*; it only passes `-f <file>` / `-p <project>` to the `docker compose` CLI. Parsing is limited to CLI *output* (JSON from `ps`/`images`, text tables from `top`) — never the compose file body.

Confirmed: `FluentDocker/FluentDocker.csproj:29-32` packages are only `Microsoft.Extensions.Logging.Abstractions`, `Microsoft.SourceLink.GitHub`, `SharpCompress`, `System.IO.Pipelines`. **No YamlDotNet.** Repo-wide grep for `YamlDotNet|ISerializer|ToYaml|YamlMember|Razor|Scriban|template` in `FluentDocker/` returns nothing relevant.

**Implication for Phase 7b:** "emitting a `models:` element via the EXISTING compose builder" requires deciding which builder is "the compose builder." The *only* builder wired into `Builder.UseCompose(...)` is the file-path-based `IComposeBuilder`, which has no model and no emitter. To emit `models:` you must EITHER (a) build a YAML emitter for the orphaned `ComposeServiceDefinition` model and wire `ComposeServiceBuilder` in, OR (b) add `models:` modeling to `ComposeServiceDefinition` + `ComposeServiceBuilder` and a new emitter. There is no existing emit path to "slot into." See §2.

## (1) How the compose builder models services & emits/loads YAML

### 1a. The POCO model (in-memory only, no (de)serialization)
- `FluentDocker/Model/Compose/ComposeServiceDefinition.cs:27` — `public sealed class ComposeServiceDefinition`. Plain POCO, one property per compose service key: `Name` (string, line 29), `Image` (line 275), `Restart` (RestartPolicy, line 31), `Environment` (`IDictionary<string,string>`, line 220), `DependsOn` (`IList<string>`, line 145), `Ports` (`IList<IPortsDefinition>`, line 349), `Volumes` (`IList<IServiceVolumeDefinition>`, line 416, get-only), `Networks` (`IList<ServiceNetworkDefinition>`, line 336), `Secrets`, `ConfigLong`, `HealthCheck`, etc. **No serialization attributes** (no `JsonPropertyName`, no `YamlMember`) anywhere in `Model/Compose/`.
- The model uses a **short/long marker-interface pattern** for polymorphic list entries:
  - `FluentDocker/Model/Compose/IPortsDefinition.cs` — empty marker interface `public interface IPortsDefinition {}`.
  - `PortsShortDefinition : IPortsDefinition` (single `public string Entry { get; set; }`) and `PortsLongDefinition : IPortsDefinition` (structured `Target/Published/Mode/Protocol`).
  - `IServiceVolumeDefinition.cs` — empty marker; `ShortServiceVolumeDefinition` (`Entry`) and `LongServiceVolumeDefinition` (`Source`/`Target`/`IsReadOnly`/`Options`).
  - **This is the exact pattern a new `models:` binding should follow** (see §2/§4).

### 1b. The fluent service builder (populates the POCO; orphaned)
- `FluentDocker/Builders/ComposeServiceBuilder.cs:17` — `public class ComposeServiceBuilder`. Holds `private readonly ComposeServiceDefinition _config = new();` (line 19). ctor `internal ComposeServiceBuilder(string name) => _config.Name = name;` (line 21).
- Fluent methods all return `ComposeServiceBuilder` (self) and mutate `_config`: `Image(string)` (23), `Volume(...)` (37, 58), `Restart(RestartPolicy)` (66), `Environment(params string[])` (77, parses `name=value` or even/odd pairs), `DependsOn(params string[])` (108), `Ports(int target, int published, PortMode mode, string protocol)` (117) and `Ports(params string[])` (125).
- **No `Build()`/`ToYaml()`/emit method.** There is no way to extract YAML or even to hand the `_config` to anyone. This builder is currently dead code — the natural home for a fluent `.Models(...)` per-service binding once wired, but it isn't wired today.

### 1c. The ACTUAL compose builder (file-path based; the one users call)
- Entry point: `Builder.UseCompose(Action<IComposeBuilder> configure)` at `FluentDocker/Builders/Builder.cs:146-158`. It does `var builder = new ComposeBuilder(_currentKernel, _currentDriverId); configure(builder);` and queues `builder.ExecuteAsync`.
- Also surfaced via `DockerCliFluentBuilder.UseCompose(Action<IComposeBuilder> configure)` at `DockerCliFluentBuilder.cs:63` (delegates to `_inner.UseCompose`).
- Interface: `FluentDocker/Builders/BuilderInterfaces.cs:97` — `public interface IComposeBuilder`. ALL methods are file/flag oriented and return `IComposeBuilder`:
  - `WithComposeFile(string path)` (102), `WithComposeFiles(params string[] paths)` (107), `WithProjectName(string name)` (112), `WithEnvironment(...)` (118/123), `WithEnvFile(string path)` (128), `WithBuild` (133), `WithForceRecreate` (138), `WithRemoveOrphans` (143), `ForServices(params string[])` (148), `WithRemoveVolumes` (153), `WithRemoveImages` (158), `WithTimeout` (163), `WithScale(string,int)` (169), `WithNoDeps` (174), `WithNoStart` (179), `WithPull` (184), `WithWait` (189), `WithWaitTimeout` (194), `WithProfiles(params string[])` (199), `ConnectToExisting(bool connect = true)` (210).
  - **There is NO method on `IComposeBuilder` that accepts a service definition or model.** It cannot describe services; it only references pre-existing `.yaml` files on disk.
- Impl: `FluentDocker/Builders/InternalBuilders.cs:149` — `internal sealed class ComposeBuilder(FluentDockerKernel kernel, string driverId) : IComposeBuilder, IDriverScopedBuilder`. Backing fields are scalars/lists (`_composeFiles`, `_projectName`, `_environment`, etc., lines 159-176). `ExecuteAsync` (line 234) resolves `IComposeDriver` via `_kernel.SysCtl<Drivers.IComposeDriver>(_driverId)`, builds a `ComposeUpConfig` from those fields (lines 251-269), calls `driver.UpAsync(...)`, and returns a `new Services.Impl.ComposeService(...)` (276). **No YAML is generated; `_composeFiles` are paths passed through verbatim.**

### 1d. Where YAML *content* is handled = NOWHERE (only CLI output is parsed)
- The driver only emits CLI args and parses CLI *output*:
  - Args assembly: `DockerCliComposeDriver.cs:261` — `private static string BuildComposeArgs(ComposeFileConfig config)` → `"compose"` + `foreach (file in config.ComposeFiles) args += $" -f {QuoteArgumentIfNeeded(file)}"` + `-p {ProjectName}` + `--project-directory {ProjectDirectory}` (lines 263-270). This is the **only** place compose files surface, and only as `-f <path>`.
  - Sub-arg builders (all `public static`, in `DockerCliComposeDriver.Args.cs`): `BuildUpSubArgs` (51), `BuildDownSubArgs` (87), `BuildRemoveSubArgs` (21), `BuildListSubArgs` (36, `"ps --format json"`), `BuildRestartSubArgs` (104), `BuildLogsSubArgs` (117), `BuildConfigSubArgs` (138), `BuildBuildSubArgs` (155), `BuildPullSubArgs` (175), `BuildRunSubArgs` (190), `BuildScaleSubArgs` (226), `BuildCreateSubArgs` (239).
  - Output parsing uses **STJ** (`System.Text.Json`) with `JsonHelper.CaseInsensitiveOptions`: `ParseServiceList(string json, ILogger)` at `DockerCliComposeDriver.Args.cs:266` handles a JSON array or NDJSON of `ComposeServiceInfo`; images parsed inline in `DockerCliComposeDriver.Info.cs:136-155`; `top` text-table parsing in `DockerCliComposeDriver.Parsing.cs:21` `ParseTopOutput`. **None of these read compose-file YAML.**
- Config DTOs that flow into the driver live in `FluentDocker/Drivers/ComposeModels.cs`: base `ComposeFileConfig` (line 10) with `List<string> ComposeFiles`, `string ProjectName`, `string ProjectDirectory`, `Dictionary<string,string> Environment`, `List<string> Services`; subtypes `ComposeUpConfig` (27), `ComposeDownConfig` (62), etc. Result/info DTOs (`ComposeServiceInfo` at 337 with `[JsonPropertyName("Service")]` on `Name` line 340, `[JsonPropertyName("ID")]` on `ContainerId` line 349; `ComposeImage` 403; `ComposeProcesses` 390) — these are for parsing CLI JSON, **not** for emitting compose files.

**Bottom line for (1):** services are modeled by `ComposeServiceDefinition` (POCO) but that model is never serialized; the live builder only references on-disk YAML files and shells out to the CLI. To EMIT YAML you must add an emitter — none exists to extend.

## (2) Where a new top-level `models:` element + per-service `models:` binding would slot in

Compose `models:` has two locations (Docker Compose spec): a **top-level `models:` map** (each entry has `model:` ref, optional `context_size`, `runtime_flags`, provider opts) and a **per-service `models:` binding** (list of model names, or a map `model-name: {endpoint_var, model_var}`).

Because no emitter exists, the design splits into model + emitter + wiring:

### 2a. Model classes (mirror existing short/long pattern in `FluentDocker/Model/Compose/`)
- **Per-service binding** (slots into `ComposeServiceDefinition`): add `public IList<IServiceModelDefinition> Models { get; } = [];` alongside the existing get-only collection `Volumes` (`ComposeServiceDefinition.cs:416`). Create marker interface `IServiceModelDefinition` (copy `IServiceVolumeDefinition.cs` verbatim — empty interface), then `ShortServiceModelDefinition { string Entry }` (the `- model-name` list form) and `LongServiceModelDefinition { string Source; string EndpointVar; string ModelVar }` (the map form `model-name: {endpoint_var:, model_var:}`). This is the **identical** pattern to `ShortServiceVolumeDefinition`/`LongServiceVolumeDefinition` and `PortsShort/LongDefinition`.
- **Top-level `models:` map**: a top-level compose document doesn't exist as a class yet (there is NO `ComposeDocument`/`ComposeProjectDefinition` type — verified by grep). If a full-document model is in scope, create `ModelDefinition { string Model; long? ContextSize; IList<string> RuntimeFlags; IDictionary<string,string> ProviderOptions }` and host it in a new top-level document class (e.g. `ComposeProjectDefinition` with `IDictionary<string, ComposeServiceDefinition> Services` and `IDictionary<string, ModelDefinition> Models`). Today services are not aggregated into any document type — `ComposeServiceBuilder._config` is a single, standalone `ComposeServiceDefinition`.

### 2b. The emitter (NEW — there is no existing one to slot into)
- You must author a YAML writer (hand-rolled `StringBuilder`, matching the project's no-extra-deps stance, OR add YamlDotNet — but note the repo currently has zero YAML deps). The emitter walks `ComposeServiceDefinition` → writes `services:` block, and for each service writes a `models:` sub-block; plus a top-level `models:` block. Then it must `File.WriteAllText(tempPath, yaml)` and feed that path into the existing pipeline via `ComposeUpConfig.ComposeFiles` (i.e., the generated file becomes a normal `-f` arg). **This temp-file-then-`-f` bridge is the only way to connect a model to the live CLI driver**, since the driver consumes paths, not content.

### 2c. Builder wiring point
- Per-service fluent: add `Models(params string[])` / `Models(Action<IModelBindingBuilder>)` to `ComposeServiceBuilder` (`ComposeServiceBuilder.cs`), mutating `_config.Models` — same shape as the existing `Volume(...)`/`Ports(...)` methods (lines 37-133).
- Project-level/top-level: this is the gap. `IComposeBuilder` (the wired builder) has no way to accept services or models. Phase 7b must add an entry such as `IComposeBuilder.WithService(string name, Action<ComposeServiceBuilder>)` and `IComposeBuilder.WithModel(string name, Action<IComposeModelSpecBuilder>)`, have `ComposeBuilder.ExecuteAsync` (`InternalBuilders.cs:234`) render the accumulated model graph to a temp YAML file BEFORE building `ComposeUpConfig`, and add the temp path to `_composeFiles`. See §4 for the recommended interface shape.

## (3) The attach-to-existing-project parse path (v3.1, commit 2c3f128 / #341)

**Key finding: the attach feature does NOT parse compose-file YAML at all.** It is identity-by-reference (project name and/or file paths) + CLI-output queries.

- Builder flag: `IComposeBuilder.ConnectToExisting(bool connect = true)` declared at `BuilderInterfaces.cs:210` (XML doc 201-209). Impl: `ComposeBuilder.ConnectToExisting` at `InternalBuilders.cs:232` sets `private bool _attachToExisting` (field at line 175).
- Attach branch in `ComposeBuilder.ExecuteAsync` (`InternalBuilders.cs:241-249`):
  ```csharp
  if (_attachToExisting)
  {
    if (string.IsNullOrEmpty(_projectName) && _composeFiles.Count == 0)
      throw new FluentDockerException(
          "ConnectToExisting requires WithProjectName and/or WithComposeFile to identify the project.");
    return new Services.Impl.ComposeService(
        _kernel, _driverId, _composeFiles, _projectName, _removeVolumes, _removeImages);
  }
  ```
  It **skips `UpAsync`** and constructs a `ComposeService` bound to the (`_composeFiles`, `_projectName`) identity. The compose file is never opened/parsed in C#.
- Target ctor: `FluentDocker/Services/Impl/ComposeService.cs:34-53` — `public ComposeService(FluentDockerKernel kernel, string driverId, List<string> composeFiles, string projectName, bool removeVolumes = false, bool removeImages = false)`. Stores `_composeFiles`/`_projectName`; later ops (`ListServicesAsync` at line 66) build a `ComposeListConfig { ComposeFiles = _composeFiles, ProjectName = _projectName }` and shell out (`docker compose ... ps --format json`), parsing **CLI JSON output** via `ParseServiceList`. State is reconciled by `RefreshStateAsync` (added in #341) off `docker compose ps` status, NOT off the file.
- So "attach" provides **no precedent for reading a compose file's `models:`**. If Phase 7b needs to *read back* `models:` from an existing file, that is a brand-new parse path (there is no compose-file reader anywhere in the repo). The only file-aware step is `WithEnvFile` (`InternalBuilders.cs:190-209`) which line-parses a `.env` file — not YAML.

## (4) How `IComposeModelBuilder` / `IComposeModelSpecBuilder` should hang off the existing `IComposeBuilder`

Follow the established lambda-sub-builder + marker-interface idioms in this codebase.

### Conventions to copy verbatim
- **Lambda sub-builder pattern**: `Builder.UseCompose(Action<IComposeBuilder> configure)` (`Builder.cs:146`) — `new ComposeBuilder(...); configure(builder);`. Mirror this: `IComposeBuilder.WithModel(string name, Action<IComposeModelSpecBuilder> configure)` constructs a spec builder, invokes the lambda, stores result.
- **Fluent return-self interfaces**: every `IComposeBuilder` method returns `IComposeBuilder` (`BuilderInterfaces.cs:97-211`). New methods must too: `IComposeBuilder WithModel(string name, Action<IComposeModelSpecBuilder> configure);` and (per-service) the existing `ComposeServiceBuilder` methods return `ComposeServiceBuilder`.
- **Marker interfaces for polymorphic entries**: empty `IPortsDefinition`/`IServiceVolumeDefinition` (`IPortsDefinition.cs`, `IServiceVolumeDefinition.cs`) with Short/Long impls. Apply to `IServiceModelDefinition` (per-service binding) exactly the same way.
- **Internal sealed builder impl exposing `IDriverScopedBuilder`**: `internal sealed class ComposeBuilder(...) : IComposeBuilder, IDriverScopedBuilder` (`InternalBuilders.cs:149`), exposing `Kernel`/`DriverId` explicitly (lines 155-158) so driver-specific extensions can resolve. Any new sub-builders that need driver awareness should follow this; the model spec builder is pure data and need NOT implement `IDriverScopedBuilder`.

### Recommended shape
- **`IComposeModelSpecBuilder`** = fluent builder for a SINGLE top-level model entry. Methods (all return `IComposeModelSpecBuilder`): `Model(string reference)` (the `model:` OCI/registry ref), `ContextSize(long)`, `RuntimeFlags(params string[])`, and provider option setters. Backed by a `ModelDefinition` POCO in `FluentDocker/Model/Compose/`. This is the analog of `ComposeServiceBuilder` (single `_config`), with `internal` ctor.
- **`IComposeModelBuilder`** (per-service binding) — if you want a richer per-service form than `params string[]`: fluent builder producing `IServiceModelDefinition` entries, e.g. `Bind(string modelName)` → `ShortServiceModelDefinition`, or `Bind(string modelName, string endpointVar, string modelVar)` → `LongServiceModelDefinition`. Hang it off the per-service `ComposeServiceBuilder` via `ComposeServiceBuilder Models(Action<IComposeModelBuilder> configure)` mutating `_config.Models`, mirroring `Volume(...)` (`ComposeServiceBuilder.cs:37`).
- **Top-level wiring onto `IComposeBuilder`**: add `IComposeBuilder WithModel(string name, Action<IComposeModelSpecBuilder> configure)` to `BuilderInterfaces.cs` (after `WithProfiles`/`ConnectToExisting`, ~line 199-210) and implement in `ComposeBuilder` (`InternalBuilders.cs`) by accumulating into a `Dictionary<string, ModelDefinition> _models = []` field (next to `_scale`/`_profiles`, lines 159-176). In `ExecuteAsync` (line 234), BEFORE constructing `ComposeUpConfig`, if any models/services were declared inline, render them to a temp YAML file and `_composeFiles.Add(tempPath)` so the existing `-f` machinery picks them up (`BuildComposeArgs` at `DockerCliComposeDriver.cs:261`). Respect the `_attachToExisting` early-return (lines 241-249) — inline models are incompatible with attach (throw, or skip emission).

### Gotchas / constraints to honor
- **500-line code-file cap** (CLAUDE.md): `ComposeServiceDefinition.cs` is already 419 lines and near-cap-aware; add `Models` property there but keep new model classes in their own files (`ModelDefinition.cs`, `IServiceModelDefinition.cs`, `ShortServiceModelDefinition.cs`, `LongServiceModelDefinition.cs`) like every other entry type. Split the new emitter into a `partial` if it grows.
- **No YAML library present** — adding `models:` emission means either hand-writing YAML or introducing a new package dependency; flag this decision explicitly. Booleans/strings must be quoted per the existing `PortsShortDefinition` doc warning about YAML base-60 parsing.
- The orphaned `ComposeServiceBuilder`/`ComposeServiceDefinition` are the natural home for the model graph, but **wiring them into `Builder.UseCompose`/`IComposeBuilder` is itself net-new work** — there is no `WithService(...)` today. Emitting `models:` "via the existing compose builder" is therefore really "build the missing model→YAML→temp-file→`-f` bridge, then add `models:` to it."
- STJ is the project's JSON tool (`JsonHelper.CaseInsensitiveOptions`, used in `DockerCliComposeDriver.Args.cs:276`); if you parse an existing compose file's `models:` back in, prefer STJ-on-converted-YAML or a YAML lib consistent with whatever you pick for emission. Per MEMORY.md gotcha: `JsonElement.TryGetInt32()` throws on non-Number — guard `ValueKind` first.
